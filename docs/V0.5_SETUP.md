# v0.5 setup

## Prerequisites

- Node.js 20.19+ or 22.12+
- npm
- Supabase CLI and Docker for local database work
- An existing Supabase project containing migrations `202607210001` through `202607220008`
- The project URL and browser-safe publishable/anon key

Never place a Supabase secret key, `service_role` key, database password, or administrator token in the dashboard or extension.

## Apply locally

From the repository root:

```sh
npm install
npx supabase start
npx supabase db reset
npm run test:db
```

`db reset` rebuilds the local Supabase database from every ordered migration and the seed. Do not point this command at production.

## Push to the linked Supabase project

```sh
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase migration list
npx supabase db push
```

Review `supabase/migrations/202607220009_v0_5_users_basic_rbac.sql` before pushing. The migration is additive: it preserves the legacy `user_profiles` capture-attribution table and creates the authoritative `profiles`, `roles`, and `user_roles` access tables.

Verify in SQL Editor:

```sql
select code, name, active from public.roles order by code;
select count(*) from public.profiles;
select routine_name
from information_schema.routines
where routine_schema = 'public'
  and routine_name in (
    'get_my_access_context','admin_list_users','admin_get_user',
    'admin_assign_role','admin_remove_role','admin_set_user_status'
  )
order by routine_name;
```

Confirm RLS is enabled on all public application tables and both Storage buckets remain private.

## Create and bootstrap the first Admin

1. In Supabase Dashboard, open **Authentication → Users → Add user**.
2. Create the first email/password user and mark the email confirmed as appropriate for your private environment.
3. Apply migration `202607220009`.
4. In SQL Editor, replace the placeholder and run this once:

```sql
insert into public.user_roles (user_id, role_id, assigned_by)
select profiles.id, roles.id, null
from public.profiles as profiles
join public.roles as roles on roles.code = 'ADMIN' and roles.active = true
where lower(profiles.email) = lower('<FIRST_ADMIN_EMAIL>')
on conflict (user_id, role_id) do nothing;
```

5. Verify exactly the intended user was assigned:

```sql
select profiles.email, roles.code
from public.user_roles
join public.profiles on profiles.id = user_roles.user_id
join public.roles on roles.id = user_roles.role_id
where roles.code = 'ADMIN';
```

There is intentionally no browser-callable “make me Admin” operation.

## Dashboard

Create `dashboard/.env.local`:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

Start it with `npm run dev:dashboard`. Production output is created by `npm run build:dashboard` in `dashboard/dist`.

## Chrome extension

Run `npm run build:extension`, open `chrome://extensions`, enable Developer mode, and load or reload `extension/dist`. Configure the same project URL and publishable/anon key in Settings. Applying Manager and Admin accounts can use business write workflows; JD Finder can use only JD capture; other roles cannot write.

## Additional users and role assignment

Create users manually in **Supabase Dashboard → Authentication → Users**. The Auth trigger creates an ACTIVE profile with no roles. That user sees Pending Access until an Admin opens **Users → Manage**, selects roles, and saves.

The fixed roles are Applier, Applying Manager, Developer, Development Manager, JD Finder, and Admin. Multiple roles form a union of access. JD Finder grants only extension JD capture plus self-profile access. v0.5 is one shared internal workspace; it has no tenant or organization isolation.

## Safe application rollback

Application code can be rolled back by redeploying an earlier dashboard bundle and reloading an earlier extension bundle. Do not casually reverse migration `202607220009` after users have been assigned roles. Removing it would discard application account status and role-assignment data and would restore incompatible owner-only policy behavior. Back up the database and design an explicit forward migration instead.
