# v1.6 tailored Resume materialization

v1.6 turns one human-approved preview into one private, Application-specific DOCX Resume. An Applying Manager or Admin selects **Create Tailored Resume** on the review page. NestJS reserves the job, renders a bounded DOCX in memory, uploads it through the caller-scoped Supabase client, and asks PostgreSQL to finalize the operation.

Finalization locks and revalidates the tailoring job, Application, original Resume, approved preview, attempt token, exact Storage path, MIME type, size, hash, and private object. In one database transaction it:

1. creates a numbered `TAILORED` Resume whose `parent_resume_id` is the source `ORIGINAL` Resume;
2. copies candidate, contact, address, links, category, education, certifications, and autofill metadata unchanged;
3. changes only summary, source-linked experience details, and skills;
4. marks the tailoring job `COMPLETED` with materialization audit fields; and
5. switches the Application's single `resume_id` to the tailored child.

The job records source and tailored Resume lineage. General Resume lists, counts, upload duplicate checks, and new Application pickers continue to expose only originals. A Resume-family duplicate trigger prevents another Application for the same JD and original/tailored family after the switch.

## Failure and retry

The reservation has a unique attempt token and a 15-minute stale-run recovery window. Concurrent materialization is rejected. If rendering, upload, or finalization fails, the API removes the exact job-specific object when possible and returns the job to `APPROVED`; the approved preview remains available for retry. A completed request is idempotent and returns its existing tailored Resume.

## Storage and access

The file is stored in the existing private `tailored-resumes` bucket under the original Resume owner's UUID and tailoring job UUID. Only an active Applying Manager/Admin can create the reserved object. Active managers can read it, and an assigned active Applier can read it only while it is the Resume attached to that Application. Downloads use 90-second signed URLs.

## Explicit boundary

v1.6 renders DOCX only. It does not render PDF, offer configurable templates, mutate the original Resume, show tailored children in the primary Resume dashboard, run Codex during rendering, auto-submit job applications, or change the extension UI. Because the Application now points to the tailored child, the existing extension Resume download/autofill path receives that file without a separate extension data architecture.
