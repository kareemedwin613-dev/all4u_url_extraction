# v1.1 Resume variants

The Resume table remains the source of both primary and Application-specific Resume files. Every row has a unique decimal `resume_number` for display while its UUID remains the API identity.

- `ORIGINAL` rows have no parent and are the only rows returned by the general Resume dashboard, counts, duplicate detection, upload management, and Application creation picker.
- `TAILORED` rows reference one `ORIGINAL` row through `parent_resume_id`. Nested tailored variants are rejected.
- Original files stay in the private `original-resumes` bucket. Tailored artifacts use the private `tailored-resumes` bucket.
- Resume number, type, and parent are immutable.
- New Applications start with an original Resume. A future protected tailoring-approval operation may replace the Application's single `resume_id` with a child from the same Resume family.

The v1.1 migration creates the schema and read boundaries only. It does not create tailored rows and does not execute Codex. That begins with the isolated tailoring-worker milestone.
