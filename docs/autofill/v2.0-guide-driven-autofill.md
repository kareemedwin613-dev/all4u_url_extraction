# Guide-driven Autofill v2.0 (phase 1)

Extension 1.9.0 · migration `202610062100_v3_157_guide_driven_autofill.sql`

The published **Application Guide** (dashboard → Application Guide) is the answer standard for Autofill. Autofill is still rule-based: it does not call an AI service, and it never submits an application.

## Flow

```text
Applier clicks Autofill in the extension
→ server checks the Application, the verified Resume profile, and the Resume's Autofill permissions
→ Resume is attached (unchanged)
→ every detected field is filled immediately and read back to verify it
→ a person reviews the whole page, completes the remaining questions, and submits
```

There is no preview or approval step. Every application is reviewed by a person after Autofill, so filling first is faster. The "Require a preview click before filling any field" Resume permission still exists for anyone who wants it. It is off on every Resume today.

## Where answers come from

| Question | Answer | Source |
| --- | --- | --- |
| Name, email, phone, address, LinkedIn | Resume profile | Verified Resume metadata |
| Location in personal details | `Miami, FL, USA` | Resume city, state (2-letter code), country |
| Each job: company, title, location, dates, current-role box, description | Resume work history, **all** roles | Attached Resume (tailored when there is one) |
| Each school: school, degree, field, dates | Resume education | Attached Resume, else its original Resume |
| Guide questions with a fixed answer (travel, relatives, consents, AI tool, …) | The guide's answer | Application Guide |
| Salary expectation | Midpoint of the JD range, e.g. `$125,000 per year`; `$150,000 per year` when the JD has no range | JD + guide fallback |
| Work authorization / sponsorship | `U.S. citizen`, Yes / No | Guide (every profile is a U.S. citizen) |
| Willing to relocate / work arrangement / how did you hear | No / Remote / LinkedIn | Guide |
| Total years of experience | Calculated from work history, overlapping roles counted once | Resume |
| Start availability | `Two weeks after accepting an offer`; date fields get today + 14 days | Guide |
| GPA | `3.8` (number fields) or `3.8 / 4.0` (text fields) | Guide |
| GitHub | `N/A` | Guide |
| Cover letter text box (optional or required) | The Application's cover letter text (tailored, or the base letter), line breaks kept | Application (same source as *Copy Cover Letter*) |
| Gender, pronouns | From the original Resume's gender | Resume (sensitive) |
| Veteran, military, LGBTQ+, transgender | The guide's answer | Guide (sensitive) |
| "I hereby state the information is true…" | Never filled | Guide marks it for a person |
| Experience with a single skill, proficiency ratings, open-ended questions | Not filled | Phase 2 |

**Sensitive answers** (gender, pronouns, veteran, military, LGBTQ+) are filled only when the Resume's *Never fill voluntary demographic, gender, pronoun, or veteran questions* permission is **off**. It is on by default. When it is on, these questions appear in the extension's list of questions a person must answer, with the guide's instructions. Tailored Resumes follow their original Resume's permissions.

## Admin controls

On each guide entry, Admins choose how Autofill treats the question:

- **Guidance only** — not autofilled (for explainer entries such as *Work Experience*)
- **Fill this answer** — a fixed answer such as `No`
- **Fill from the Resume or job description** — one of the sources in the table above, with an optional fallback
- **Never autofill** — a person answers; Autofill also stops every other rule from filling it

Admins can add *other wordings* for a question. `[Company]` matches the employer's name. A one-word wording such as `Languages` must be the whole question, so *Programming languages* is not filled with `English`. Saving Autofill settings does not create a new published version of the entry.

The guide page also lists **Questions Autofill could not answer**: the employer's wording (never the answer), how often it was seen, and the last job site, with *Add to guide* and *Dismiss*.

## How a field is matched

Three rule sets propose answers for each field on the page:

1. Contact and history fields (`personal-field-adapter.js`). It knows which section a field is in, so a *Location* inside a job entry is that job's location. Repeated job and school entries are numbered from the page's own indexes, or by order when there are none. Sentence-style labels are skipped, so *I hereby **state**…* is not the State field.
2. Application Guide questions (`guide-field-adapter.js`).
3. The Resume's Answer Library (`screening-field-adapter.js`), kept for the Resumes that use it.

`arbitrateAutofillCandidates` gives each field to exactly one rule: the highest score wins, and ties go to the guide. No field is filled twice. Dropdown and radio answers are matched to the page's wording (`option-matching.js`): `United States` ↔ `United States of America`, `CA` ↔ `California`, `No` ↔ `I am not a protected veteran`, `7` ↔ `6-10 years`.

## Forms that add jobs and schools one at a time (Workable)

Workable collects Experience and Education behind a **+ Add** button that opens an inline editor for one entry. For each job and school on the Resume, Autofill:

1. clicks **+ Add** (`button[data-ui="add-section"]`);
2. fills title, company, description, and the current-role box (or school, field of study, and degree);
3. picks start and end dates in Workable's month picker. Dates with only a year are left for the reviewer rather than given an invented month;
4. clicks the entry's own Save button (`data-ui="save-section"`) and checks that the saved entry appears.

Entries are added oldest first because Workable shows the newest-added entry at the top, so the page ends up in Resume order. A section that already has entries, typed by a person or parsed by Workable, is left alone. Only buttons with `type="button"` are clicked, so the application is never submitted. If Workable rejects an entry, it stays open with Workable's message for the reviewer, and no further entries are added in that section. Results appear in the side panel as *Experience 1: Senior Engineer at Acme* and similar.

This was verified end to end on a live Workable posting in Chrome (`repeatable-sections.js`, `WORKABLE_SECTIONS`). Other sites can reuse it by describing their selectors the same way.

## Ashby forms

Verified end to end on a live Ashby posting in Chrome:

- Ashby's `<label for>` often points at an id the control does not have, and radio questions are a `<fieldset>` whose first `<label>` is the question. When a control has no linked label, Autofill reads the question from its own field container (`containerQuestion`).
- *Preferred First & Last Name* receives the full name; *Legal First/Last Name* receive the first and last names.
- Search-as-you-type dropdowns get up to 3 seconds for results. Locations are searched by city and matched on city plus state (*Miami, Florida, United States*).
- When several options share the same Yes/No, the one saying the candidate will **not** need sponsorship wins, since every profile is a U.S. citizen.

The extension's in-page scripts are built as separate IIFE bundles. Built as plain scripts, the Resume script and the Autofill script shared minified global names in the page's extension context and overwrote each other, which could break Resume attachment after Autofill had already run in the same tab.

## Greenhouse forms and experience questions

Verified end to end on a live Greenhouse job board in Chrome:

- react-select dropdowns open from the same pointer and mouse event sequence a click produces, and options are read only from that field's own listbox (`aria-controls`). The page's hidden phone-country list is never used. The *Country* picker shows only the dial code once chosen (`+1`), so a choice counts as confirmed when the displayed text is part of the clicked option.
- Hidden helper inputs (react-select's `aria-hidden` "required" input, the phone widget's search box, reCAPTCHA) are ignored.
- A contact field that matches more than one rule (a "Country" label that also mentions the neighbouring "Phone") keeps every candidate, so the right field wins once the real phone field takes Phone.
- **Yes/No experience questions** are answered from the Resume (`resume-evidence.js`): the total years in the work history against the number asked, and skills from the skills list, job titles, and job descriptions. A skill not on the Resume is **No**. A skill that is listed but whose roles show fewer years than asked is left for a person. "Such as" examples need one match; "A, B, and C" lists need half.
- When the page asks for a contact value the Resume does not have (for example no LinkedIn URL), the side panel says *Not on this Resume* instead of leaving the field silently empty.
- Identity, contact details, address, and links come from the original Resume (migration v3.159), so edits such as adding a LinkedIn URL reach every tailored copy.

## Privacy

- The extension receives guide questions and wordings, never their answers, until it fills. Values are computed in the side panel.
- Unanswered questions store the employer's wording only. Emails, links, and long numbers are removed server-side, and only the session's owner can record them.
- Field outcome telemetry keeps keys, confidence, and outcome codes, never values. Guide fields are recorded as `guide.<entry id>`.

## Deployment

1. Review the migration, then apply `202610062100_v3_157_guide_driven_autofill.sql`. It adds the guide autofill columns and seeds rules for the published guide by question prefix, without overwriting rules an Admin already set. It also adds 7 published entries for the confirmed decisions, adds `resumes.gender`, the new Autofill context function, and the unanswered-question tables.
2. Deploy the API and dashboard. The API calls `get_application_autofill_context_v3157`, so deploy it after the migration.
3. Set each original Resume's gender (Resume page → Autofill Permissions → Gender).
4. Decide whether to turn off *Never fill voluntary demographic…* on the original Resumes so gender, pronoun, and veteran answers fill.
5. Convert free-text education (see below).
6. Build the extension (`npm run build:extension`) and reload it, or publish 1.9.0.

## Education conversion (one time)

All original Resumes keep education only as free text, which Autofill cannot split into School / Degree / Major. Run:

```text
node scripts/education/convert-legacy-education.mjs --out <folder outside the repo>
```

It reads production read-only and writes `education-review.html` (each Resume's text beside the proposed entries, with uncertain ones flagged) and `education-apply.sql`. After a manager checks the review page, apply it with `npx supabase db query --linked -f <folder>/education-apply.sql`. Each update is skipped if that Resume changed since the file was generated. The free text is kept. Newly tailored Resumes will show education from the structured entries, which render the same way.
