# v0.9.0 Resume Answer Library

v0.9.0 stores reusable, explicitly reviewed application answers on the Resume aggregate. It does not create a Candidate identity table and does not infer answers from a Resume, job description, or AI service.

## Data model

Migration `202607290028_v0_9_0_resume_answer_library.sql` creates `public.resume_application_answers`, keyed by `resume_id`, with one row per fixed answer key. The initial safe keys are work authorization, sponsorship, relocation, available start date, desired salary, years of experience, and remote-work preference.

The database validates the key/type/value combination, bounds question patterns, rejects prohibited sensitive categories, records creator/reviewer timestamps, and keeps archived answers with `active = false` for auditability. RLS is enabled. Direct authenticated reads are restricted to Applying Managers and Admins; writes are available only through protected PostgreSQL functions.

## API

All dashboard traffic uses the authenticated NestJS API:

- `GET /api/v1/resumes/:resumeId/application-answers`
- `POST /api/v1/resumes/:resumeId/application-answers`
- `PATCH /api/v1/resumes/:resumeId/application-answers/:answerId`
- `DELETE /api/v1/resumes/:resumeId/application-answers/:answerId`

The controller requires `APPLYING_MANAGER` or `ADMIN`, validates UUIDs and DTOs, rate-limits requests, and uses the request-scoped Supabase client so RLS remains active. Answer values are not included in request logs.

## Dashboard and extension boundary

Applying Managers and Admins receive an **Answer Library** tab on Resume detail. They can add, edit, verify, activate, and archive answers with Ant Design controls. Appliers cannot browse or mutate the library.

For an assigned Application, the existing Application-scoped autofill context now includes only answers that belong to that Application's active Resume and are both `active` and `VERIFIED`. v0.9.0 exposes this safe snapshot; field matching and filling are intentionally deferred to v0.9.1.

## Verification during Resume upload

New Resume uploads collect the canonical personal, contact, address, link, summary, and structured experience metadata before the private file and database row are saved. The Admin must select **Reviewed and accurate**. The backend then writes the Resume and metadata together with `profile_review_status = VERIFIED`, `profile_reviewed_by` set to the authenticated Admin, and `profile_reviewed_at` set by the backend.

Changing any upload field clears the confirmation. Existing and legacy Resumes retain the **Edit Resume Metadata** page for corrections and one-time review. This is not a second metadata store: the page edits the same `resumes` columns and `structured_content` aggregate used during upload.

## Deployment and verification

Apply the migration with `npx supabase db push`, then redeploy the API/dashboard build. Run `npm run check` for local automated coverage and `npm run test:db` against a started local Supabase stack. Manually verify manager CRUD and an assigned Applier autofill-context response before treating the live workflow as accepted.
