# Resume-owned Autofill Roadmap: v0.8.9 to v1.0

## Baseline and architectural decision

This roadmap supersedes the Candidate-table assumptions in the original v0.8.5-to-v1.0 roadmap. The deployed v0.8.8 correction makes `public.resumes` the canonical autofill aggregate:

- A Resume ID is the profile ID used throughout the autofill workflow.
- Personal/contact, primary address, links, and review metadata are columns on `public.resumes`.
- Ordered employment, education, and certifications are stored in `resumes.structured_content` schema version 3.
- Autofill reads existing reviewed metadata. It does not parse the Resume file or `resume_text` again.
- `profile_review_status = 'VERIFIED'` is required before profile values can be offered for autofill.
- Editing identity, contact, address, link, employment, education, or certification metadata must reset review status to `NEEDS_REVIEW` unless the same authorized transaction explicitly verifies the final result.
- No `candidates`, `candidate_profiles`, `candidate_addresses`, `candidate_links`, `candidate_employment_history`, `candidate_education`, or `candidate_certifications` tables will be reintroduced.

Migration `202607290024_v0_8_8_resume_autofill_metadata_correction.sql` is the deployed baseline. Every future database change must use a new migration version; applied migrations `023` and `024` must never be rewritten.

## Canonical Resume autofill shape

| Autofill data | Canonical storage |
| --- | --- |
| Name, email, phone | Columns on `resumes` |
| Primary address | Columns on `resumes` |
| LinkedIn, GitHub, portfolio | Columns on `resumes` |
| Employment history | `structured_content.professional_experience[]` |
| Education history | `structured_content.education[]` |
| Certifications | `structured_content.certifications[]` |
| Legacy unstructured education | `structured_content.education_legacy_text` for review only |
| Review state and reviewer | `profile_review_status`, `profile_reviewed_by`, `profile_reviewed_at` |
| Schema version | `structured_schema_version` and `profile_schema_version` |

Every repeatable record must have a stable string `id` and deterministic display order. APIs may present typed objects, but must update the Resume aggregate atomically rather than creating parallel child records.

## Naming and compatibility transition

The existing `/api/v1/candidates/:resumeId/...` endpoints and `Candidate*` shared contract names are compatibility interfaces only. Their identifier is already a Resume ID; they do not represent a Candidate database entity.

During v0.8.9:

1. Add canonical `/api/v1/resumes/:resumeId/autofill-profile` read/update routes.
2. Move implementation ownership from the API `candidates` module to a `resume-autofill` module.
3. Introduce `ResumeAutofill*` shared contract names.
4. Keep the old routes and types as thin deprecated aliases through v1.0.
5. Do not duplicate database logic. Compatibility routes must call the same service.

The Application endpoint remains the safest entry point for the extension. The extension receives a Resume ID only through an authorized Application context and must not select an arbitrary Resume.

## Shared invariants for every remaining milestone

- Dashboard and extension call NestJS only; they do not query Supabase tables or RPCs directly.
- NestJS verifies the Supabase JWT and uses a request-scoped user client so RLS remains active.
- Normal requests never use a service-role or privileged key.
- The extension never stores Resume bytes, signed URLs, profile values, or screening answers in persistent browser storage.
- Server logs and analytics never include profile values, Resume contents, signed URLs, or access tokens.
- Preview precedes fill; verification follows every attempted fill.
- The extension never clicks a final submit button.
- Sensitive or legally consequential answers are never inferred.
- Autofill operates on a stable Application, Resume, profile schema version, and Resume `updated_at` snapshot. A stale preview must be rejected and regenerated.
- Every new table uses RLS, explicit grants, foreign-key indexes, audit timestamps, and protected mutation functions where direct writes would bypass workflow rules.

## v0.8.9 — Personal/contact autofill

Implementation checkpoint: source and automated coverage completed. Migration `202607290025` and deployed browser acceptance remain pending until explicitly authorized/performed.

### Goal

Fill standard personal and contact fields from the verified Resume aggregate.

### Backend and contracts

- Add `GET /api/v1/applications/:id/autofill-context` as the extension-facing endpoint.
- Authorize from the Application: assigned active Applier, Applying Manager, or Admin.
- Return only fields required for the requested autofill action, plus `resumeId`, `resumeUpdatedAt`, `profileSchemaVersion`, and `reviewedAt`.
- Return `409 PROFILE_REVIEW_REQUIRED` when the Resume profile is not verified.
- Return `409 AUTOFILL_CONTEXT_STALE` if a supplied session snapshot no longer matches the Resume.
- Add canonical Resume-profile routes and deprecated compatibility aliases described above.
- Do not return `resume_text`, Storage paths, hashes, or Resume bytes from the autofill-context endpoint.

### Extension

Implement `FieldDetector`, `FieldNormalizer`, `FieldMatcher`, `FieldValueResolver`, `AutofillPreview`, `FieldFiller`, and `FillVerifier` for:

- first, middle, last, and full name
- email and phone
- address lines, city, state/region, postal code, and country
- LinkedIn, GitHub, and portfolio URL

Detection may use labels, `autocomplete`, ARIA attributes, name/id, placeholder, input type, fieldset legend, nearby text, and select options. Confidence policy:

- 90–100: ready, selected by default
- 70–89: review required, not selected by default
- below 70: unsupported

Preview state is memory-only and tied to the extension session and Resume snapshot. Filling is user-triggered, individual failures do not block unrelated fields, and every result is verified from the DOM.

### Acceptance gates

- Automated detector, matcher, normalization, confidence, preview, fill, verification, stale-snapshot, authorization, redaction, and regression tests pass.
- Manual tests cover ordinary text/select fields on approved test pages.
- No production job-site claim is made without a real browser test.

## v0.9.0 — Resume answer library

### Goal

Store reusable, explicitly reviewed answers that are not Resume facts.

### Database

Create `resume_application_answers`, keyed by `resume_id`. Do not create a Candidate identity table. Suggested fields:

- `id`, `resume_id`, normalized `answer_key`
- `question_patterns` as a bounded text array
- `answer_type`, typed `answer_value` JSON
- `review_status`, `reviewed_by`, `reviewed_at`
- `active`, `created_by`, `created_at`, `updated_at`

Use a unique constraint on `(resume_id, answer_key)`, validate allowed answer types, and prohibit sensitive answer keys at the database/API boundary. An active, reviewed answer can be used only with the Resume that owns it. Multiple Resumes for the same person intentionally remain independent in this model.

### APIs and UI

- Manager/Admin CRUD through `/api/v1/resumes/:resumeId/application-answers`.
- Assigned Appliers receive only verified, active answers through the Application autofill context.
- Ant Design Resume detail tab for review, activation, and audit metadata.
- No answer values in list telemetry or logs.

## v0.9.1 — Standard screening autofill

Use verified `resume_application_answers` for supported yes/no, radio, select, short-text, date, and numeric fields.

- Match normalized labels and approved question patterns.
- Exact normalized-key matches outrank patterns.
- Ambiguous matches require review and remain unselected.
- Never infer work authorization, sponsorship, desired salary, relocation, or availability; use only an explicit reviewed answer.
- Never support demographic, disability, veteran, medical, religion, race, ethnicity, gender, sexual-orientation, or criminal-history answers.
- Show the source (`Reviewed answer`) and confidence in preview without persisting the value in session analytics.

## v0.9.2 — Employment and education autofill

### Data source

Read `professional_experience[]`, `education[]`, and later `certifications[]` directly from verified `structured_content` v3. No child tables and no Resume reparsing are permitted.

### Behavior

- Support repeated sections, add-section controls, current-role checkboxes, and site-specific month/year formatting.
- Offer all records, most recent N, Resume-visible records, or manual record selection.
- Preserve stable record IDs and Resume ordering.
- Treat `education_legacy_text` as non-fillable until a Manager/Admin converts it to reviewed structured records.
- If structured content or review state changes after preview, require a fresh preview.
- Verify each generated section and field independently.

### Editing

Continue using atomic Resume aggregate mutations. Add certification mutation support to the canonical Resume-autofill API if required. Every mutation resets review status and records the authenticated editor through existing audit fields or a focused Resume-metadata history table if detailed diffs become a confirmed requirement.

## v0.9.3 — ATS adapter framework

Introduce an adapter registry without changing storage:

```text
Exact-domain adapter
→ ATS-family adapter
→ Generic HTML adapter
→ Manual fallback
```

Each adapter receives an immutable, memory-only autofill context and exposes detection, preview metadata, fill, attachment, and verification capabilities. Adapters never fetch Supabase, never submit forms, and never persist profile values. Build specific adapters only from measured generic-adapter failures on approved test sites.

## v0.9.4 — Autofill sessions and feedback

Extend the existing `application_extension_sessions` model rather than creating a competing `autofill_sessions` table.

Add only the metadata needed for recovery and measurement, such as Resume snapshot identifiers, adapter/version, target-domain hash or normalized domain, detected/selected/succeeded/failed counts, and terminal error code. Add `application_extension_session_fields` and optional `autofill_feedback` only when field-level outcomes are required.

Field records may store normalized field keys, confidence, outcome, adapter, and error code. They must never store filled values, Resume text, question text containing personal data, signed URLs, or tokens.

## v0.9.5 — Privacy, consent, and security hardening

- Add bounded `autofill_preferences` JSON to `resumes` only if per-Resume controls are required: allow attachment, allow profile fields, allow reviewed answers, require review for every field, and prohibit sensitive questions.
- Reuse `application_extension_sessions` as the Resume-access/autofill audit trail; add a separate audit table only if the existing event model cannot satisfy an explicit retention/reporting requirement.
- Minimize host permissions and request optional site access where practical.
- Add CSP, secret scanning, dependency review, log-redaction tests, privacy disclosure, retention rules, and session cleanup.
- Ensure archived Resumes immediately lose attachment and autofill eligibility.
- Ensure review status and consent are revalidated server-side at context retrieval and immediately before a resumed fill.

## v0.9.6 — Reliability and recovery

- Observe relevant DOM mutations and re-detect invalidated fields.
- Support multi-step forms without carrying raw values in persistent storage.
- Persist only a non-sensitive recovery pointer: session ID, Application ID, target origin, step identifier, and Resume snapshot version.
- Re-fetch authorized autofill context after service-worker restart or expiry.
- Detect changed Resume snapshots, expired sessions, navigation to a different origin, adapter-version mismatch, and detached inputs.
- Provide safe retry, Re-scan Page, refresh Resume access, cancellation, and manual fallback.
- Report partial success field-by-field; never repeat already verified fills blindly.

## v1.0 — Production readiness

Release only after the complete workflow passes:

```text
Application authorization
→ verified Resume-owned context
→ optional secure Resume loading/attachment
→ detection and preview
→ explicit human selection
→ fill and verification
→ human submission
```

Required gates:

- Automated database, API, dashboard, extension, integration, security, lint, type-check, and production-build suites pass.
- RLS and unauthorized RPC/API tests cover every new table and mutation.
- Supported-browser manual tests cover session recovery and partial failure.
- Approved real-site tests establish the supported generic and ATS-specific matrix.
- Privacy disclosure, retention behavior, permissions, logging, and secret scanning are reviewed.
- No automatic submission exists.
- No Candidate persistence tables exist.
- No frontend or extension code accesses Supabase data APIs directly.
- No privileged key or private credential is exposed.

Before every migration: compare the linked ledger, test against a database containing the originally deployed `023`, and verify upgrade plus fresh-reset paths. Production pushes remain an explicit user-authorized action.

## Milestone completion report

For each milestone report:

- canonical Resume fields and APIs used
- files and migrations changed
- direct data access removed or confirmed absent
- authorization and RLS behavior
- tests, lint, types, and builds with actual results
- browser, live-site, staging, migration, and deployment tests not performed
- security properties and known limitations

Do not claim a live autofill, attachment, migration, deployment, browser, or ATS result unless it actually ran.
