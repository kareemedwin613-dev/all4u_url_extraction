# Autofill phase 2 plan: technical, Resume-specific, and JD-specific questions

Status: plan only, not implemented. Builds on [v2.0 guide-driven Autofill](v2.0-guide-driven-autofill.md).

## Goal

Answer the questions phase 1 leaves unanswered, during Autofill and from the attached (usually tailored) Resume and the job description:

- technical questions: experience with a skill, years with a skill, proficiency ratings, certifications;
- open-ended questions: *Why do you want to work here?*, *Describe a relevant project*, *Tell us about yourself*;
- JD-specific questions: requirements checks (*Do you have 5+ years of React?*), team or product questions.

Autofill may be slower in exchange (decided 2026-10-06). As in phase 1, answers are filled immediately and a person reviews the page before submitting.

## Decisions already made

| Topic | Decision |
| --- | --- |
| Skill not on the Resume | Answer **No** (or 0 years) without asking the model |
| Proficiency | From the skill's years: under 1 → Beginner (2 of 5); 1–3 → Intermediate (3); 3–5 → Advanced (4); 5+ → Expert (5) |
| Which Resume | The Resume attached to the Application, which is the tailored one when there is one |
| When | Live, during Autofill, after the phase 1 rules |

## Design

```text
phase 1 rules fill what they can
→ deterministic skill rules (no model) answer skill questions
→ remaining eligible questions go to the API in one batch per page
→ the API asks the model, grounded in the Resume, JD, and Application Guide
→ the extension fills the answers and marks them "Drafted from the Resume — review"
→ a person reviews and submits
```

### Step 1: deterministic skill answers (no model)

- Recognize the skill a question names using the JD's `detected_skills`, the Resume's skills text, and an alias list (`JS` = JavaScript, `k8s` = Kubernetes, `Postgres` = PostgreSQL). The model is only used to name the skill when none of these match.
- **Has the skill?** Yes if the skills text or any role's description mentions it; otherwise No.
- **Years with the skill:** add up the roles whose title or description mentions it, counting overlaps once.
- **Proficiency:** the mapping above, matched to the page's scale (1–5, Beginner–Expert, or similar).
- **Certification:** Yes only if the Resume lists it.

### Step 2: model-drafted answers

The extension sends the API only what the page shows: question wording, control type, answer options, a character limit if there is one, and whether the question is required. It never sends questions that the guide marks *Never autofill*, sensitive questions, or legal declarations.

The API (`POST /api/v1/extension-sessions/:id/autofill-drafts`):

1. Authorizes the session like the Autofill context does: assigned Applier, verified profile, Resume permissions.
2. Builds the prompt from the attached Resume text and the JD text (as `get_application_qa_context_v3154` already does for *Copy Q&A Prompt*), the published guide, and the fixed facts: U.S. citizen, remote, salary rule, and LinkedIn as the source.
3. Treats page text, the Resume, and the JD as data, not instructions.
4. Asks for strict JSON, one item per question: an option index, a short text answer within the limit, or `SKIP` with a reason.
5. Rejects answers that contradict the Resume's employers, dates, degrees, or certifications, or that choose an answer for a skipped legal question.
6. Caches answers per Application and normalized question, so re-scans and retries cost nothing.
7. Uses the existing provider layer (OpenAI/Codex in the matching and tailoring workers). The model, timeout, and monthly budget are settings.

### Step 3: record what was drafted

- Store each drafted answer with its question per Application (new table, RLS like Applications), so reviewers and the screenshot AI review can check it.
- Field outcome telemetry records `draft.<hash>` keys with outcome only. The field-key check gains a `draft` prefix.
- Feed questions the model skipped into the existing *Questions Autofill could not answer* list.

## Safety rules

- The model never answers legal declarations, sensitive self-identification, or anything the guide marks *Never autofill*.
- Facts come only from the Resume and JD: employers, titles, dates, degrees, certifications, and legal eligibility are never invented.
- Answers respect character limits and the page's options; a choice that matches no option is not filled.
- Every drafted field is labelled in the side panel so the reviewer knows it was written by the model.

## Milestones

1. **2a — Skill rules (no model).** Skill recognition, has-skill, years-with-skill, proficiency, certifications. Measure with the unanswered-question list.
2. **2b — Model drafts.** The endpoint, prompt, JSON validation, caching, side panel labels, and a budget guard.
3. **2c — Records.** Drafted-answer storage, screenshot-review integration, and telemetry.
4. **2d — Tuning.** Use the unanswered-question list and reviewer corrections to add guide entries and improve the prompt.

## Open decisions

1. **Invented examples.** The current *Copy Q&A Prompt* lets the model create a plausible project when the Resume has no matching example. Should live drafts be allowed to do that, or only use what the Resume says?
2. **Model and budget.** Which provider and model to use, and the monthly spend limit.
3. **Long answers.** The default length for open-ended answers with no character limit (for example, 120 words).
4. **Cover letter boxes.** Paste the Application's existing tailored cover letter instead of drafting a new answer?
