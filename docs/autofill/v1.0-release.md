# Deterministic Autofill v1.0

This release uses rules, verified Resume metadata, structured Resume sections,
and manually reviewed Answer Library entries. It does not call OpenAI, Codex,
or another AI service and it never submits a job application.

## Supported coverage

Greenhouse, Workable, Lever, and iCIMS receive named ATS adapters. Other sites
use the conservative Generic HTML adapter. Personal/contact fields, current
employment, repeated employment and education fields, approved screening
answers, and the JD salary midpoint are supported where the page exposes a
standard input, select, textarea, date, month, number, radio, or checkbox.

## Privacy and recovery

Autofill preferences are stored on each Resume and enforced by PostgreSQL.
Sensitive voluntary answers are excluded by default. Resume files remain in
private Storage and are held only in extension memory while attaching. Recovery
stores identifiers, origin, adapter version, Resume snapshot timestamp, and
sanitized outcomes—never field values or Resume content. Managers may remove
telemetry older than 7–365 days with the protected cleanup RPC.

## Installation and updates

For unpacked development installs, run `npm run build:extension`, open
`chrome://extensions`, select **Load unpacked**, and choose `extension/dist`.
After each update rebuild and press **Reload** on that extension card. Store
distribution should use Chrome Web Store automatic updates and a fixed extension
ID; publishing is a manual release action and was not performed here.

## Deployment checklist

1. Apply migrations 032–035 in order and inspect their result.
2. Deploy the API/dashboard with the documented public Supabase and API settings.
3. Run `npm run check` and `npm run test:db` against a linked local/test project.
4. Manually verify each named ATS, recovery after navigation/reload, archived
   Resume rejection, role boundaries, and private file access.
5. Confirm CSP, CORS, redirect allowlists, logs, rate limits, and retention.

The extension keeps broad HTTP(S) host access because the product explicitly
supports arbitrary job sites and the configured workflow requires all-site
access. It remains user-triggered and does not submit forms.
