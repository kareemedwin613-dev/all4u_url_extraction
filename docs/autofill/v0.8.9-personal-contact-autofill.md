# v0.8.9 Personal and Contact Autofill

## Delivered flow

1. An authorized user starts Autofill from an Application.
2. The existing 15-minute `AUTOFILL` extension session opens or focuses the job URL.
3. `GET /api/v1/applications/:id/autofill-context` validates the Application, session owner, session action/status/expiry, caller access, active Resume, verified review state, and HTTP(S) target.
4. The API returns only supported reviewed Resume values plus the Resume snapshot timestamp and schema version. It never returns Resume text, file metadata, Storage paths, hashes, or bytes.
5. The tracked page detects standard personal/contact controls and sends descriptors—not page contents—to the side panel.
6. The side panel shows confidence, values, and checkboxes. Confidence 90+ is selected by default; confidence 70–89 requires explicit selection.
7. Immediately before filling, the API revalidates the expected `resumeUpdatedAt`. Changed metadata produces `AUTOFILL_CONTEXT_STALE` and nothing is filled.
8. Only selected fields are sent to the tracked content script. Each field dispatches normal input/change/blur events and is verified from its resulting DOM value.
9. The extension reports per-field success/failure and never submits the form.

## Supported keys

- first, middle, last, and full name
- email and phone
- address lines, city, state/region, postal code, and country
- LinkedIn, GitHub, and portfolio URLs

## Resume-owned API transition

Canonical metadata routes now use `/api/v1/resumes/:resumeId/...`. Existing `/api/v1/candidates/:resumeId/...` routes remain compatibility aliases and call the same Resume-owned service. No Candidate persistence table exists.

## Database

Migration `202607290025_v0_8_9_application_autofill_context.sql` adds only the protected `get_application_autofill_context_v089` function and its authenticated grant. It creates no table and must be pushed before live Autofill can use this milestone.

## Limitations

- Generic standard HTML inputs, textareas, and selects are supported; custom widgets, iframes, and Shadow DOM require later adapters.
- Only one best field per supported key is previewed.
- Select values require an exact normalized option value or label match.
- Employment, education, certifications, and screening questions remain later milestones.
- Browser/job-site manual acceptance testing is required after migration and deployment.
