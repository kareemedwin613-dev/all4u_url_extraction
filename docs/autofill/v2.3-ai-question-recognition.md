# AI question recognition

Status: implemented (migration v3.161). Builds on [v2.0 guide-driven Autofill](v2.0-guide-driven-autofill.md) and the [phase 2 plan](v2.1-phase-2-llm-plan.md).

## What it does

Job sites word the same question in many ways. When Autofill meets a question its rules cannot answer, it asks which known answer the question is asking for:

- an Application Guide entry, such as work authorization or salary;
- a Resume answer, such as requires sponsorship or start date;
- or none: an essay question, a specific skill, something we don't hold.

The answer is remembered by the question's wording and reused for every Applier and profile. Each new wording costs one model call; after that it is a table lookup.

Fields filled this way show an **AI-matched** tag in the side panel's field list. As always, a person reviews the page before submitting.

## Flow

1. Autofill scans the page with the usual rules.
2. The questions the rules could not answer go to the API in one request per page. Only the employer's wording and the option labels are sent.
3. The API looks each wording up in `autofill_learned_wordings`. Known wordings are answered from the table.
4. New wordings go to the model the Admin chose (Grok by default) with the list of known answers. The model returns a target and a confidence for each.
5. Results with confidence 80 or more are used and saved. Results below 80 are not used and not saved, so a person answers them.
6. The extension adds the recognized wordings to the matching Guide entry or Resume answer for this page and scans again. The usual matchers then fill the fields, so every existing safety rule still applies: sensitive questions, attestations, legal statements and "never autofill" entries are still left for a person.

Matching ignores case and punctuation. "Are you authorized to work in the U.S.?" and "are you authorized to work in the US" are the same wording. A differently phrased question is a new wording and costs one more model call.

## What is sent and stored

| | Contents |
| --- | --- |
| Sent to the AI provider | Employer question wording, option labels, the names of known answers (Guide entry questions, Resume answer types). Emails, links and long numbers are removed first. `store: false` is set. |
| Never sent | Answers, candidate name or contact details, Resume or JD content |
| Stored | The scrubbed wording, the answer it maps to, confidence, model, dates |

Only the API's server key can write the table. Appliers read it through their own live Autofill session.

## Cost controls

- Learned wordings are reused, so spend falls as common wordings are learned.
- A monthly cap (default $40) is enforced; past the cap, unanswered questions are left for a person until the next month.
- `AUTOFILL_AI_ENABLED` is the off switch.
- At most 30 questions per page, 1,500 output tokens per call, and a 10 second timeout. A failed or slow call never blocks Autofill.
- Wordings unused for six months are removed automatically.

## Questions without a standard answer (v3.162)

When the AI finds no known answer, it also says what kind of question it is. Only the kind is stored, never an answer.

| Kind | Example | What happens |
| --- | --- | --- |
| Needs a standard answer | "Are you open to a hybrid schedule, 3 days in office?", "Are you open to contract roles?" | Shown under **Needs a standard answer** in **Learned by AI**. An Admin clicks **Add standard answer**, writes the answer once and publishes. Autofill fills it for every candidate from the next page, with no AI. |
| Depends on the profile | "Years of hands-on Kubernetes?", "Do you hold a CPA licence?" | Left alone: the resume-based rules, or AI drafting later |
| Open-ended | "Why do you want to work here?" | Left for AI drafting (step 3) |
| Statement | Consents, attestations, headings | Left for a person |

**Add standard answer** opens the usual guide editor with the question and the employer's wording already filled in, and the Autofill mode set to *Fixed answer*. Publishing the entry removes the learned "no standard answer" row, since the entry now answers that wording itself. Appliers are never asked to set standard answers during Autofill.

Placeholders such as "Select" or "Search", and plain contact labels such as "First name" or "Email", are never sent to the AI. Filling contact details is the contact rules' job.

## Overview: AI Autofill Usage & Cost

Admins see this section on the Overview page. It follows the page's Reporting Period:

- This month's spend against the cap, with a month-end projection at the current pace. It turns red when the projection is over the cap.
- AI cost in the period, with model calls and tokens.
- The share of unanswered questions answered from the learned table at no AI cost. This should rise week by week.
- The number of new wordings sent to the AI.
- Cost per autofilled application, for planning at higher volumes.
- Daily spend.
- Status: AI on or off, the model, the number of learned wordings, and a warning if wordings are not being saved.

Usage is stored per hour, so days follow the viewer's own time zone, as the rest of the Overview does. The monthly cap is measured per UTC calendar month. Only counts are stored: no question text, answers or candidate data.

The Application Guide page shows Admins a **Learned by AI** section. It lists each wording, what it maps to and how often it is used, plus this month's question count and spend. **Remove** deletes a wrong match, and the AI decides again next time.

**Correct** (v3.166) sets what a wording really asks for:
- a contact field, filled from the Resume (for example "LinkedIn Profile: Please provide the URL…" → LinkedIn URL);
- a published standard answer;
- a Resume answer;
- or no standard answer, with the kind of question.

A corrected wording applies to every applier from their next page, and the AI never overwrites it. The AI can also choose contact fields itself.

Separately, a label written as "Name: instruction" ("GitHub: please include a link…") is now matched by its name, so such boxes no longer reach the AI at all.

## Settings (Admins, on the dashboard)

The Overview's **AI Autofill Usage & Cost** section has a **Configure** button. It is Admin-only; the API and database also refuse changes from anyone else.

- **On/off:** the off switch.
- **Provider:** Grok (xAI) or OpenAI. A provider without its key on the server cannot be switched on.
- **Recognition model and drafting model:** chosen from models the server can price (`apps/api/src/autofill-ai/model-catalog.ts`), so cost tracking and the cap stay accurate.
- **Monthly cap**, in dollars.
- **Test this model:** runs ten sample questions against the chosen model and shows accuracy, speed and cost before saving. The cost is a fraction of a cent and is not counted against the cap.
- **Recent changes:** who changed what, and when.

Changes apply from the next Autofill page, with no redeploy. API keys are never entered or shown in the dashboard.

## Access per person (v3.165)

Everyone starts with AI **Off**, including people added later. An Admin gives each person one of three levels:

| Level | What AI does for that person |
| --- | --- |
| Off | Nothing. Learned wordings still answer, because a learned wording is a table lookup with no model call and no cost. |
| Match questions | Matches new question wordings to the standard answers. |
| Match + draft answers | Also drafts answers to open-ended questions, for a person to review ([v2.5](v2.5-ai-drafted-answers.md)). |

The **Configure** on/off switch still turns AI off for everyone, whatever each person's level is.

Admins set levels in two places:
- the **AI access by applier** table under *AI Autofill Usage & Cost* on the Overview;
- the **AI Autofill** card on each applier's page.

Both show each person's usage for the Reporting Period:
- Autofill runs, and how many of them used AI (a run counts once, however many AI calls it made);
- questions matched by AI, and questions answered from the learned table;
- answers drafted;
- AI cost.

The API enforces the level, so an older extension cannot get around it. A database without v3.165 reads as Off for everyone. Every change is kept with who made it. Per-person usage is counted from v3.165 onwards; earlier usage was stored only as totals.

## Setup (Vercel environment variables)

| Variable | Value |
| --- | --- |
| `XAI_API_KEY` | The xAI (Grok) key. Required to use Grok. |
| `OPENAI_API_KEY` | The OpenAI key. Optional; lets Admins switch to OpenAI. |
| `SUPABASE_SECRET_KEY` | Already used for dashboard pairing. Without it, recognized wordings are used but not remembered, so every page pays again. |
| `AUTOFILL_AI_ENABLED`, `AUTOFILL_AI_PROVIDER`, `AUTOFILL_AI_MODEL`, `AUTOFILL_AI_MONTHLY_CAP_USD` | Optional starting defaults (off, `xai`, the provider's default model, `50`) until an Admin first saves settings in the dashboard. |

Then apply migration `202610081000_v3_161_autofill_learned_wordings.sql` and redeploy.

To compare models from the command line, run this from `apps/api`, with keys in `apps/api/.env`:

```
npx tsx --env-file=.env test/autofill-ai-try.ts xai grok-4.20-0309-non-reasoning
```

## Providers and data

| | Grok (xAI) | OpenAI |
| --- | --- | --- |
| Endpoint | `https://api.x.ai/v1/chat/completions`, strict JSON schema | `https://api.openai.com/v1/responses`, strict JSON schema, `store: false` |
| Retention | 30 days for abuse monitoring, no training. Zero data retention can be turned on team-wide in the xAI console; recommended before AI drafting (step 3). | Per the OpenAI account's settings |
| Default model | `grok-4.20-0309-non-reasoning` ($1.25 in, $0.20 cached, $2.50 out per 1M tokens) | `gpt-6-luna` ($0.10 in, $0.50 out) |

The unchanging part of each request (instructions plus the list of known answers) comes first, so most input tokens are billed at the cached rate.

## Security boundary

AI calls are allowed only in the isolated workers and in `apps/api/src/autofill-ai/`. `npm run security:check` enforces this and also flags any direct `api.openai.com` call elsewhere. This module is the API's only provider call, and it handles no candidate data.
