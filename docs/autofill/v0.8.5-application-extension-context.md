# v0.8.5 Application-to-extension context

This milestone connects authorized Application actions in the dashboard and extension without exposing Resume bytes.

## Flow

1. An assigned active Applier, Applying Manager, or Admin selects **Load Resume** or **Autofill**.
2. The authenticated client creates a 15-minute `application_extension_sessions` record through the NestJS API.
3. The dashboard bridge sends only the session ID, Application ID, action, target URL, and expiration to the extension.
4. The service worker validates the configured dashboard origin and message schema, opens or focuses the job URL, and stores the short-lived active session in `chrome.storage.session`.
5. The extension loads minimal Application context from NestJS using its own Supabase access token. PostgreSQL rechecks `application_actor_can_view` under RLS-aware user identity.
6. Resetting the context cancels the server session and clears the browser session state.

## Security boundary

- No Resume bytes are downloaded in v0.8.5.
- No Storage bucket/path, signed URL, access token, refresh token, Resume text, saved answer, or Candidate profile field is included in the handoff.
- The existing Resume `user_id` is treated as the uploader, not inferred as Candidate ownership.
- Candidate context contains the existing display name only and reports `profileAvailable: false` until v0.8.8 provides verified Candidate Profiles.
- Session table writes are RPC-only; authenticated callers receive an own-session, Application-authorized read policy.
- The extension never submits a job application.

## Endpoints

- `GET /api/v1/applications/:id/extension-context`
- `POST /api/v1/applications/:id/extension-sessions`
- `PATCH /api/v1/extension-sessions/:id`

The production dashboard bridge is restricted to `https://all4u-url-extraction.vercel.app`; localhost origins are included for development. Preview Vercel domains require an explicit reviewed manifest match rather than a wildcard.
