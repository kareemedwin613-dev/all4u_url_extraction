# v0.5 troubleshooting

## Profile was not created

Confirm migration `202607220009` applied and trigger `sync_auth_user_access_profile_after_insert_or_update` exists on `auth.users`. Re-save the Auth user email/metadata or insert the missing profile from `auth.users` using the migration’s backfill pattern. Do not invent a different UUID.

## Pending Access

The account is ACTIVE but has no active role. An Admin must assign one through **Users → Manage**. Do not store a role only in user metadata or browser storage.

## Account Inactive

An Admin set `profiles.status` to INACTIVE. Reactivate it through Admin Users. Supabase Auth may still issue a valid session, but RLS intentionally denies platform data.

## Admin navigation is missing / first Admin not bootstrapped

Run the idempotent first-Admin SQL in `V0.5_SETUP.md`, verify the email, refresh the page, and sign in again. The dashboard never calls an Auth Admin API.

## Role assignment fails

Verify the caller is an active Admin, the target profile exists, and the role is one of the five active codes. Browser clients must call `admin_assign_role`/`admin_remove_role`; direct `user_roles` writes are intentionally denied.

## Last active Admin error

This is expected when a change would leave no active Admin. Activate/assign another Admin first, then retry. The safeguard is serialized in PostgreSQL and cannot be bypassed by enabling a UI control.

## Navigation is visible but the query is denied

Refresh to reload access context. Then inspect `profiles.status`, active role rows, and the v0.5 RLS policies. Navigation is only UX; PostgreSQL remains authoritative.

## User cannot open a resume file

Confirm the user is ACTIVE with APPLIER, APPLYING_MANAGER, or ADMIN; the object is in the private `original-resumes` bucket; and the signed URL request uses the stored bucket/path. Developer roles do not grant candidate-file access.

## Developer unexpectedly sees business data

Check for an additional APPLIER, APPLYING_MANAGER, or ADMIN assignment. Then verify the old owner policies were replaced by the v0.5 policy names. Developer alone must receive zero business rows.

## Extension save button is hidden or disabled

Applying Manager, JD Finder, and Admin have `EXTENSION_BUSINESS_WRITE`. JD Finder is capture-only; it does not receive shared dashboard business access. Applier is intentionally read-only. Pending, inactive, Developer, and Development Manager accounts do not receive business write controls.

## Dashboard still shows only owned records

Confirm migration `202607220009` replaced the owner-only policies. Search read services for stale client filters such as `.eq('user_id', currentUser.id)` and remove them from read-only list/detail queries. Keep ownership checks in write services and RLS.

## Session is valid but access context fails

Run `select public.get_my_access_context()` as the authenticated user through a local test or API client. Confirm a matching `profiles` row exists. Network errors must be retried; they are not Pending Access.

## Migration policy-name conflict

Inspect `pg_policies` for the table/schema and compare names with migrations `202607210002`, `202607210003`, `202607220004`, `202607220007`, and `202607220009`. Do not edit an applied migration. Add a forward compatibility migration using only verified `drop policy if exists` names.
